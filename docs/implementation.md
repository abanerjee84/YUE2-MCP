# Implementation and FLUX3-MCP review

The reference is `E:/TOOLS/FLUX3-MCP`, inspected at commit `89a3e4c`. Its core design is one FastAPI worker shared by CLI, stdio MCP and HTTP MCP clients. Adapters submit immediately to a SQLite queue. A single thread owns inference; request IDs make retries idempotent. The client uses a file lock to start one service. Settings select the RTX 3060 by UUID before the inference runtime initializes.

The reusable parts are orchestration: `config.py`, `jobs.py`, `client.py`, `install.py`, `download.py` and `metrics.py`. YUE2-MCP adapts those modules with its own home, ports, launcher and MCP identity. It preserves unrelated agent settings during registration and creates backups. It adds a second seed for token sampling and measures the native child PID rather than the Python adapter PID.

FLUX's inference layer is specific to images: Diffusers modular pipelines, the INT8 ConvRot transformer, a Qwen3-VL NF4 encoder, reference-image upload/normalization, PNG previews and PyTorch allocator telemetry. None of these inference dependencies are needed by the music worker.

The YuE2 replacement is `YueBackend`. It owns one localhost-only native `yue-server` process, hidden on Windows. The authenticated public wrapper remains the job owner. The native process handles model stages and returns multipart audio, ABC score, semantic replay data and acoustic latents. The wrapper persists artifacts before marking success. Canceling the current job terminates only this owned child; the next request restarts it. Shutdown closes the queue and releases the child.

Windows service autostart uses a hidden WMI process outside the stdio client's process job, so disconnecting an adapter does not kill the shared queue. It uses [Win32_Process.Create](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/create-method-in-class-win32-process) with an explicit environment and startup settings. The environment helper restores the public Program Files paths from Windows registry settings: this driver's NVML initialization fails when MCP's restricted environment omits both PROGRAMFILES and PROGRAMW6432. Regression tests exercise both behaviors. No startup task or Windows service registration is installed.

Native source is pinned to `ServeurpersoCom/yue2.cpp` commit `5a9500fd2979ab99fc82895877aadf8583acbabb`; its GGML submodule is `210138933b22221ced02943b7b6e4308610ab530`. Model files are pinned separately with SHA-256 values in `models.py`. `vendor/`, environments and weights are local installation artifacts and are ignored by Git.

The default profile is Q8_0, F32 VAE, batch one, 16,384-token context, flash attention, VAE tile core 256 and retained model weights. Local qualification observed a 6,949 MiB short-song peak and 7,909 MiB for a 219-second song. A subsequent 30-second job took 18.0 seconds with no model reloads. Strict stage eviction remains an explicit lower-memory alternative, measured at 4,215 MiB for the short song. Semantic guidance is explicitly 1.0, avoiding the second KV stream used by guidance. Eight steps are the speed preset; listening quality relative to 32 steps requires evaluation. Duration is a ceiling and reaching it can truncate a song. The service reports that condition rather than claiming exact-duration composition.

The Windows driver sampler reports dedicated and shared allocations for the native PID. A sampled dedicated-memory watchdog stops jobs above the configured 10.5 GiB budget. This is a guard, not a CUDA allocator hard limit; a transient peak between samples can escape it. Explicit CUDA device selection prevents a switch to the other GPU. GGML retains a CPU backend for unsupported operations and host staging, so this wrapper does not claim the same all-tensors-on-CUDA audit as FLUX.

The native backend binds to 127.0.0.1 on a separate port. That internal endpoint has no bearer authentication; the user-facing FastAPI/HTTP MCP endpoint authenticates requests and rejects foreign browser origins. This is a local single-user deployment. Do not expose the native port to a network.

Validation consists of queue/service tests, real subprocess stdio MCP sessions, Streamable HTTP MCP sessions and separate hardware generation runs. Audio checks establish nonempty finite 48 kHz stereo samples; they do not establish singing quality, lyric fidelity or musical quality. Hardware results belong in `docs/benchmark-*.json` and the final validation report.
